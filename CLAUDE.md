# Задача для Claude Code: «Генератор статей» для линкбилдинга (iGaming)

Ты — senior-разработчик. Помоги мне довести до рабочего состояния десктоп-программу для Windows, которая массово генерирует SEO-статьи со ссылками через Gemini API и сама проверяет их на соответствие ТЗ. Пиши код и общайся на русском.

В папке проекта уже лежит рабочая версия 1.1.1 (Electron): `main.js`, `preload.js`, `package.json`, `src/` (`core.js`, `app.js`, `index.html`, `styles.css`). **Начни с того, что прочитаешь весь код и кратко расскажешь, как он устроен.** Ничего не переписывай с нуля: улучшай маленькими шагами, после каждого шага проверяй.

## 1. Контекст

- Я линкбилдер. Мне нужно примерно 100 статей за 2 недели, в среднем 10–20 в день.
- Работаю на Windows. Мой план работы ведётся в Excel; Google Таблиц в процессе нет.
- Статья = гостевой пост на сайте-доноре со ссылкой на сайт-акцептор (проект, онлайн-казино).
- Готовый HTML я копирую из программы и вставляю в админку донора вручную.
- Gemini API на **бесплатном тарифе**, у каждой модели свои лимиты (см. раздел 6).

## 2. Входные данные

Я копирую строки из Excel (Ctrl+C) и вставляю их в программу (Ctrl+V). Формат строки «Плана работы», колонки A…L:

`Domain | Data | Anchor | Link Page | Login | Password | Comment | Type link | Price | Costs | Project | Linkbuilder`

- **Донор** = колонка A (Domain), например `paradisechick.com`.
- **Анкор** = колонка C (Anchor), например `betano casino`. Бывает голый URL — тогда это валидный анкор.
- **Акцептор** = колонка K (Project), например `https://betanonl.net/`.
- Заголовков в копии обычно нет, поэтому по умолчанию колонки берутся по позиции. Если заголовки есть, их нужно распознать.
- Если в ячейке ссылка с подписью (например «Whytewold Emporium» со ссылкой на wwemporium.com), для донора и проекта берётся **адрес ссылки** из `text/html` буфера. Колонку анкора не трогать: там важен именно текст.
- Подходит и вставка из трёх колонок: Донор · Анкор · Проект.

## 3. ТЗ к статье (это требования руководителя, не менять)

- Пишется на **языке донора**, как носитель, без кальки.
> С версии 1.2.0 (21.10.2026) ТЗ = промпт команды, по которому статьи писались вручную. Эталоны — `test/fixtures/team-*.html`. Решения пользователя: структура как в промпте, бренд «как в примерах» (в роли примера в аналитике и наблюдениях рынка), тема только iGaming, цитата — обычный `<p>` в кавычках.

- `<h1>` — уникальный, тематический, **без бренда**, не начинается с «Как» (How, Wie…). Дальше **ровно 7 разделов `<h2>`** (короткие подзаголовки), никакого текста между `<h1>` и первым `<h2>`.
- Каждый раздел — отдельный аспект темы, 5–6 длинных информативных предложений, от 600 знаков; плотность одинаковая до конца.
- Объём задаётся в настройках **в знаках с пробелами**, по умолчанию 4500–6500 (эталоны команды — 5500–6700; в промпте команды написано 3500–4500, но 7 × 600 знаков в него не помещаются).
- В трёх разных разделах (не во 2-м): небольшой `<ul>`, небольшая `<table>` с `<th>` (желательно числа), небольшой `<ol>`.
- **SEO-ссылка ровно одна**, **во 2-м разделе** (там нет бренда), не в 1-м: `<a href="АКЦЕПТОР">АНКОР</a>`. Анкор дословно, без изменения падежа, формы и регистра. Других `<a>` нет.
  - **Вариант А** (язык донора = язык ссылки): ссылка органично в абзаце 2-го раздела, рядом уточнение вроде «игровая платформа», «развлекательная платформа».
  - **Вариант Б** (языки разные): во 2-м разделе отдельный `<p>` с короткой цитатой в кавычках на языке ссылки, ссылка внутри цитаты (не в начале), рядом «entertainmentplatform» и т.п. Говорит специалист из страны акцептора, **имя вымышленное**, каждый раз разное; атрибуция на языке ссылки («…“, aldus …»). Без перевода цитаты, без `<blockquote>`.
- **Бренд — 6 раз**: по одному в разделах 1, 3, 4, 5, 6, 7; во 2-м и в `<h1>` бренда нет. Формы по приоритету: «бренд + casino/kasino/kasyno/казино» → бренд как есть → бренд через пробел. Бренд — пример в аналитике, наблюдениях рынка, поведении игроков, технологиях; не обзор, не преимущества, никаких призывов играть, регистрироваться, вносить депозит, бонус-кодов. Не больше 5% текста.
- Цифры умеренно, типичные значения и диапазоны. **Нельзя выдумывать** названия конкретных исследований, организаций, изданий, авторов (кроме специалиста в цитате) и даты.
- Запрещённые фразы (клише и «маркеры ИИ») задаются списком в настройках.
- Вывод: чистый HTML без атрибутов (кроме `href`), без Markdown, без `<html>`/`<body>`.
- Режим темы: «iGaming» (тема про казино и ставки) или «Стык с донором» (тема на стыке ниши донора и игр).

## 4. Что уже есть в версии 1.1.1 и должно остаться

- Мелкие вещи код исправляет сам: анкор дословно, `href`, Markdown.
- Данные хранятся локально в `%APPDATA%\Генератор статей\data.json`. Обновление — заменой `resources/app.asar`.
- **Авто-отчёт не нужен.** Его убрали специально.

## 5. Уроки, которые уже стоили времени (обязательно учесть)

1. **Не отправлять несколько статей в одном запросе.** Пробовали пачки по 3: ответ шёл дольше таймаута, запрос повторялся и тратил лимит, всё зависало. **Одна статья — один запрос.**
2. **Таймаут запроса — около 150 секунд, максимум один повтор.** Потом статья получает «Ошибка» с причиной, а очередь идёт дальше. Нельзя, чтобы одна статья держала очередь 10+ минут.
3. **В статусе нужен секундомер** («пишу статью · 34 сек»), иначе непонятно, работает ли программа или висит.
4. **Не включать `thinkingLevel: 'minimal'`.** Рабочий вариант — `'low'`. Для `gemini-2.5-*` используется `thinkingBudget: 0`.
5. **Ответ 429 нужно разбирать.** Читать `QuotaFailure.quotaId` и `RetryInfo.retryDelay`:
   - `PerDay` → сразу переходить на следующую резервную модель;
   - `quotaValue: 0` → модель недоступна на бесплатном тарифе, тоже переходить дальше;
   - лимит в минуту → ждать ровно `retryDelay`.
6. **Запросы равномерно распределять по времени** (по умолчанию 5 в минуту ≈ раз в 12 секунд), чтобы не ловить лимит в минуту.
7. **404 «model no longer available, use models/X»** → автоматически переключиться на X и сохранить в настройках.
8. **Не использовать алиас `gemini-flash-latest`:** он был медленным, до 200 секунд на статью.
9. Перед любыми изменениями логики генерации **проверь их на мок-Gemini** (имитация ответов, 429, таймаутов). Реальный лимит — 20 запросов в день на модель, тратить его на отладку нельзя.

## 6. Реальные бесплатные лимиты (по моему AI Studio)

| Модель | RPM | RPD |
|---|---|---|
| gemini-3.8-flash | 5 | 20 |
| gemini-3.5-flash | 5 | 20 |
| gemini-2.5-flash-lite | 10 | 20 |
| остальные | 0 или неизвестно | |

Основная модель — `gemini-3.8-flash`. Резервные — `gemini-3.5-flash, gemini-3.7-flash, gemini-3.6-flash, gemini-2.5-flash-lite`. Когда работает, статья генерируется за 7–50 секунд. Главное ограничение — дневной лимит. Возможно, я подключу оплату; тогда нужна настройка «статей одновременно» 2–3.

## 7. Что сделать дальше (по порядку, каждый пункт отдельно с проверкой)

1. **Анти-футпринт** (важно для SEO: 100 статей с одинаковым скелетом — это паттерн):
   - код случайно выбирает **план структуры** для каждой статьи: в каком разделе (2–4) стоит `ul`/`table`/`ol`; элемент после абзацев или между ними; 2–3 абзаца в разделе; 3–5 пунктов или строк; в каком разделе форма «бренд + казино»;
   - позиция ссылки: 1-й абзац ~45%, 2-й ~45%, 3-й ~10%;
   - 10–15 разных подводок к цитате в варианте Б;
   - план передаётся в промпт, а проверка допускает ссылку в 1–3 абзаце;
   - **проверка похожести**: сравнивать новую статью с готовыми по шинглам из 5 слов. Совпадение >30% — критично, переписать; 15–30% — мелочь.
2. **Кнопка «Копировать с форматированием»** (`clipboard.write({ html, text })`) для визуальных редакторов в админках.
3. **Подсказка языка для .com-доноров**: открыть сайт (`lang`, текст страницы), подставить язык и попросить подтвердить.
4. **Резервная копия данных** одной кнопкой и восстановление.
5. **Ключ API хранить зашифрованным** через Electron `safeStorage`.
